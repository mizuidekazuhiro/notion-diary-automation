# 日記の根拠・欠損・配信状態の運用

## 判定の資格と限界

Mood未入力は目的変数に含めない。確認できた1〜5のみを使い、1〜2を低気分の観測として扱う。同日の重複は独立標本にしない。不一致の重複は除外する。

探索の最低条件は有効12日、目的変数の両群各3日、露出群と比較群各3日。12日は既存モデルの厳しい側の最低件数、3日は既存の組合せ支持件数を保持したもの。両群・比較群の最低条件は、ゼロ件や極端に小さい分母から関連を作らないために追加した。これらは予測精度・医学的閾値・個人確率の校正を意味しない。

記録品質を危険因子にせず、上昇幅0は採用しない。同じ観測日集合の組合せは一つとする。条件を満たした探索結果も関連であり、原因や検証済み予測ではない。現在の気分リスクは校正された予測器がないため判定不能とし、低リスクと表示しない。

## 入力と日付

| 入力 | 扱い |
|---|---|
| 本人のNotes・音声メモ | 本人の報告。感情・目的を付け足さない |
| 滞在区間 | 位置・時間の記録。勤務・飲食等の実施を証明しない |
| 決済 | 支払の記録。訪問・購入品・本人の飲食を証明しない |
| 予定 | 実施未確認の予定 |
| Done / Drop | 完了・取りやめへの状態変更。イベント実施や成果に変えない |
| AI要約 | 推定を保持し、次の生成で確定事実に格上げしない |
| Study / Workout | 計算済みの値と取得状態を生成・表示まで伝える |

位置・支出の窓は既存の05:00 JST。睡眠候補のキーは既存の開始時刻（なければ終了時刻）から5時間を引く規則を保持し、対象日一致を必須にする。翌日助言に過去ページの睡眠を優先流用しない。

Anki復習は04:00 JSTの学習日を維持する。Healthcareのアプリ利用セッションは開始時刻、日記の手入力Studyは終了時刻を基準とする既存仕様を保持する。日跨ぎの長いセッションでは所属日が異なることがある。一律統一していない。Ankiのみのセッション上限・既存の復習時間上限も変更していない。

欠測日はカレンダー上に空欄を保持し、前の記録行を「前日」としない。未入力・取得失敗・解析失敗・日付違い・確認済み0を分ける。過去値をコピーして補わない。保存されたStudy 0は原本確認がない限り未確認0である。天気は取得対象日を記録し、ページ日付と一致しない天気を同日のMood分析に使わない。

## 生成・保存・配信

日記の各文に情報源と確度を持たせ、数値・予定・状態変更・推定を検査し、別モデルでも照合する。検証情報には私有の入力スナップショット、本文hash、入力hash、対象日、プロンプト版を保持する。公開ログ・GitHub本文に原本やメール本文は保存しない。

生成方式・成功/判定材料不足/縮退・棄却理由・代替文・モデルを保存する。文字数を埋める定型文にしない。モデル・プロンプト・分類契約の変更はhashに反映し、正常で同一の結果は再利用する。反復は入力不足や縮退を診断する情報として記録する。

送信前に実際の件名・本文・HTMLと保存済み根拠を検査し、同じ内容をSMTPへ渡す。重大な不整合は送信しない。取得不足を本文に明示して判定を控える場合は警告として配信できる。成功とするF判定の監査metadata欠落は引き続きエラーである。

SMTP前にautomation-stateブランチへ原文を含まない配信claimをCAS保存する。送信受付が不明、または送信後の状態保存に失敗した場合は自動再送しない。配信・品質・metadata保存・配信後確認を別状態として残す。後段の品質出力は送信前スナップショットを再利用する。

## モデルと評価

| 用途 | 採用 | 設定 |
|---|---|---|
| Notes抽出 | gpt-6-luna | reasoning none |
| 位置要約・日記 | gpt-6.1-terra | reasoning none |
| 助言・整合性 | gpt-6.1-sol | reasoning low |

共通OPENAI_MODELによる上書きを避け、用途専用変数で設定する。Chat Completions、構造化出力、4096出力上限、120秒の読取timeout、Retry-After対応を実装。GPT-6系にはtemperatureを送らない。助言の判定材料が不足する日はAIを呼ばない。

公式の[モデル資料](https://developers.openai.com/api/docs/models/gpt-6.1-terra)・[Sol](https://developers.openai.com/api/docs/models/gpt-6.1-sol)・[Luna](https://developers.openai.com/api/docs/models/gpt-6-luna)・[料金](https://developers.openai.com/api/docs/pricing)を2026-11-07に確認。

5種類の保存データを、同じ入力・共通の厳格な検査で現行モデルと2回比較した。[第1回](https://github.com/mizuidekazuhiro/notion-diary-automation/actions/runs/42339060993)、[第2回](https://github.com/mizuidekazuhiro/notion-diary-automation/actions/runs/42339509137)。84呼出しのusageによるStandard単価推計は$0.16834045。推論tokenは出力token内、cache write追加分・再試行・棄却も対象とする。請求実費ではない。

第2回でTerraの日記は5/5の契約検査を通過。miniの4/5は事実精度80%を意味しない。独立照合でminiの滞在→勤務・Done→会食等の追加も検出した。Terraは状態変更・支払・翌日を区別した。Solの誤文拒否は予測精度ではなく、正しい文の受理も別の合成対照で確認する。分類は中立/空欄に加え、疲労・ストレス・睡眠不調・運動の合成対照を本番と同じ正規化経路で検査する。

## 計測と適用確認

調査対象の旧生成では30日履歴の2回取得が合計約289秒、外側429再試行24回、共通AIログ22回。新経路は同一実行で履歴contextを共有しbulk GET 1回。内側HTTP再試行を除き、外側だけでRetry-After/バックオフを管理する。モデル別usage・試行・遅延、取得時間を分けて記録する。

Notes分類は変更分だけ再実行し、モデル/入力/プロンプト版を含むNotion保存結果またはキャッシュを使う。ファイル保存失敗を計数する。Actionsキャッシュの書込権限とv2キーを設定し、合成canaryで実際の保存を確認した。

mainのCI成功から正式Deploy workflowを実行する。自動適用の直前に最新mainと検査SHAを比較し、古いCIの遅着で巻き戻さない。`/health`のversionでGitHub版と本番を照合する。`Diary Production - Read-only Verification`はbulk GETだけを使い、根拠を持つ保存日記が1件以上なければ失敗する。F予測の品質とSMTPはこの読取検証の対象外として明示する。

直近7暦日の修復は、生成済み6件のみのプレビューを独立照合済み。原本全体を暗号化アーティファクトと私有の復元用記録へ退避する。派生本文と生成hash/時刻/metadataのみ更新し、元Notes・音声・位置・支出・学習原本・タスク状態、既送信メールは変更しない。通常実行の結果は次回の運用ログで別途確認する。
